# Changelog

## 0.3.2

- **New: search / filter the current list.** A search field in the toolbar (focus it with ⌘F, or via the Edit → Find menu) narrows the file browser or the open archive's contents to entries whose name or path matches what you type. Clearing the field restores the full list.
- **Fixed: duplicate "Name" columns could appear in the file/archive list (especially after toggling columns from the header menu).** When the column set is rebuilt, some macOS versions don't release the old outline (Name) column even after it's unbound, so `removeTableColumn` leaves it behind and a second Name column is added on top — and the doubled order then got written back to preferences (`fileColumnOrder` → `[name, name, size, …]`). The rebuild now does a final pass that removes any left-over duplicate-identifier columns, and the stored order is de-duplicated on launch and on every column move, so the duplicates are gone and can't come back.
- **Improved: the Settings → View columns pane is more compact.** With all the new columns, the old sparse 2-wide × 14-tall toggle grid pushed the live preview off-screen. The toggles are now laid out as a single-column "file browser" block beside a two-column "archive browser" block, roughly halving the height so the column switches and the preview fit together.
- **Fixed: opening a `.gpg` (or browsing a `.szs` as a virtual folder) offered the full file-management right-click menu on what is temporary, decrypted content.** The decrypted bytes live in a scratch directory that's cleaned up automatically, so Rename / Duplicate / Make Symlink / Cut / Paste / Move to… / Delete / New File·Folder (and Add to Archive / Create Signed Manifest / Encrypt to GPG) made no sense there — and could delete or move the temporary copy. The context menu in this read-only virtual browse is now restricted to view/export/inspect actions: Open, Open With, Quick Look, Show Package Contents, Hash, Copy, Get Info, and Reveal in Finder.
- **Fixed: the global menu bar flickered constantly — top-level menus were hard to even open.** When the browser was showing a folder that the system touches in the background (Spotlight / `.DS_Store` / thumbnail caches on Desktop, Downloads, the home folder, …), the folder watcher fired continuously and reloaded the listing every ~120 ms. Even when the directory contents were unchanged, two `@Published` properties (the empty archive list and the status text) were reassigned on every reload, and `@Published` doesn't dedupe identical values — so the model republished several times a second, which rebuilt the whole menu-bar command set and tore down any open menu (you had to long-press to keep a menu open). The folder reload now compares against the current state and touches **no** observable property when nothing actually changed, so a quiet folder produces zero spurious menu rebuilds.
- **Removed: the "Create self-extracting archive" (SFX) option.** It relied on a Windows `.exe` stub module (`7zCon.sfx` / `Default.SFX` …) that the macOS builds of 7-Zip and RAR don't ship, so it always failed with "cannot find specified SFX module" — and even if it worked, the output would be a Windows-only executable that can't run on a Mac. Rather than ship fake support, the option (and its backend `-sfx` plumbing) is gone.
- **Fixed: a `.siz` / `.szs` signed by a key you've set to Marginal / Full / Ultimate trust was wrongly shown as "signer's key imported but not trusted".** The verify badge was reading gpg's computed *validity* (which stays "undefined" for an imported key you trust but haven't signed with your own key) instead of the *ownertrust you set*. It now reads the ownertrust — consistent with the trust dropdown — so a key you've trusted verifies as trusted (green), and only Never / not-yet-set keys show the "not trusted" note.
- **New: four more archive list columns** — Accessed time, Host OS, Characteristics, and Symlink Target — matching what the official 7-Zip file manager shows. Toggle them in the column-header menu, the View menu, or Settings → Columns. They're populated from `7zz`'s detailed listing; formats/entries that don't report a field show blank.
- **New: a "Symlink Target" column in the file browser** shows where a symbolic link points. (For local files, "access time" is already covered by the existing "Last Opened" column, so no separate Accessed column is added there.)
- **Fixed: a `.szs` signed by a key that isn't *Ultimately* trusted failed to open ("Failed to parse signed manifest").** When the signing key's trust was Marginal / Full / Never (anything but Ultimate), gpg prints a "this key is not certified with a trusted signature" warning whose continuation line is an indented fingerprint — which leaked into the manifest text SimpleZip extracted from gpg's combined output and broke the JSON parse. The signed manifest is now read by parsing the `.szs` file's clearsigned armor directly (the same bytes gpg verifies), independent of trust level; gpg is still used to establish the signature's authenticity. (`.siz` was never affected — its metadata is read straight from the container.)
- **Fixed (signature trust): a valid signature from an untrusted key was shown in green ("all good").** A `.siz` / `.szs` signed by a key you've marked **Never** — or simply haven't trusted — produces a `GOODSIG`, but a good signature only proves the file wasn't tampered with, not that you trust the signer. The verify badge now turns **orange** for an untrusted-but-valid signature (matching the existing icon and "signer's key imported but not trusted" title), and the summary explains the key is in your keyring but not marked trusted — instead of the green "all good" wording. Trusted (Marginal / Full / Ultimate) signatures stay green.
- **Groundwork: Archive Diff / Compare engine.** A pure comparison core that pairs two archives' entry lists by path and reports added / removed / changed (type, size, CRC, modified time, encryption) / unchanged. Fully unit-tested; the compare UI lands in a later build.
- **Groundwork: in-archive search/filter engine.** A filter that narrows a listed archive by name or full path, kind (files/folders), encrypted-only, and size range. Fully unit-tested; the search field UI lands in a later build.
- **Groundwork: compression presets.** A model + persistence layer to save named create-options (format, level, method, …) as reusable presets, with passwords and GPG secrets stripped before they're stored. Fully unit-tested; the save/apply UI lands in a later build.

## 0.3.1

- **New: `.szs` signed manifests now carry the same tamper-proof recipient instructions (template mode).** Like `.siz`, a created `.szs` embeds a human-readable note in the (clearsigned, so tamper-proof) manifest: what it is, how to verify the signature, and how to check each file's SHA-256 by hand with `gpg` + `shasum`. The note you type in the create dialog's Description becomes the sender message at the top. The verify sheet shows it (collapsible, with Copy). Manifest schema bumped to v2 (v1 still accepted; pre-0.3.1 builds won't open v2 `.szs`).
- **New: Secure Bundle — a `.siz` you can hand to someone now carries human-readable, tamper-proof recipient instructions.** When you create a signed `.siz`, SimpleZip embeds a plain-text note in the signed `metadata.json` explaining what the container is, who signed it, who it's encrypted for, how to verify and decrypt it with SimpleZip, and how to do the same by hand with `tar` + `gpg` (no SimpleZip needed). Because it lives in the *signed* metadata — not as an extra file in the container — it's tamper-proof (editing it breaks the signature) and the `.siz` "exactly three files" hardening is untouched. The verify sheet shows the instructions (with a Copy button) when you open such a `.siz`. The create dialog also gains an optional **"Note to recipient"** field so you can add your own message, which is included in the same tamper-proof instructions. (`.szs` already has its own title/description, so it's left as-is.)
- **Fixed (archive safety, follow-up): editing an encrypted ZIP still used an empty password.** The earlier fix carried over the open password for header-encrypted 7z, but an AES/ZipCrypto **zip** lists its contents *without* a password (only extraction needs one), so SimpleZip never captured it — and an in-archive edit would have written new entries unencrypted (or failed). SimpleZip now detects that the archive's entries are encrypted and prompts for the password before the first edit (Add / Delete / Rename / New / write-back), caching it for the session. The safe write path still guarantees the original is untouched on any failure.
- **Fixed: keys in SimpleZip's private keyring ("独立 GNUPGHOME") couldn't actually be used — they showed up but every operation failed or was hidden.** SimpleZip's private keyring is a separate, isolated `GNUPGHOME`, but several flows only ever ran gpg against the system `~/.gnupg`, so a key that lived only in the private keyring was unusable:
  - **Signing a `.szs` / `.siz` with a private-keyring key now works.** `gpg --detach-sign` / `--clearsign` ran against `~/.gnupg` and couldn't find the private-keyring secret key, so signing failed; they now use the key's own keyring.
  - **"Encrypt to GPG" now lists private-keyring recipients.** The recipient picker only showed `~/.gnupg` keys; it now lists both keyrings and encrypts against the right one. (One gpg encryption can only use one keyring, so mixing recipients from `~/.gnupg` and the private keyring in a single encryption is blocked with a clear note.)
- **Fixed: the GPG trust-level dropdown only seemed to work for "Ultimate".** It displayed the *computed validity* instead of the *ownertrust you set*, so setting Never / Marginal / Full appeared to snap back to "Not set" (only Ultimate happens to make validity match). The dropdown now reads the actual ownertrust (via `gpg --export-ownertrust`), and "Not set" is selectable again to clear a trust setting.
- **Fixed: newly created GPG keys had no encryption subkey, so they couldn't receive encrypted files.** The new-key sheet promised an "Encryption — encryption subkey (automatic)", but `gpg --quick-generate-key <uid> ed25519 default` only ever produced a sign+certify primary (`scSC`) with no encryption subkey (Ed25519 itself can't encrypt). SimpleZip now explicitly adds an encryption subkey after the primary — `cv25519` for an Ed25519 key, same-size RSA for an RSA key — matching what the sheet shows. Keys created before this fix remain sign-only; create a new key to get encryption.
- **Fixed: the "Encrypt to GPG" recipient picker offered sign-only keys.** Keys without any encryption capability (no `e` in capabilities and no encryption subkey) can't be encryption recipients — gpg rejects them with "unusable public key". The picker now lists only encryption-capable keys (from either keyring).
- **Hardened: creating a key now fails loudly if the required encryption subkey can't be added** instead of silently returning a sign-only key. The partially-created primary key is removed so the operation is all-or-nothing; the optional authentication subkey still fails softly (the key stays usable).
- **New: add a subkey (sign / encrypt / authenticate) to an existing key.** A key created before the encryption-subkey fix (or any sign-only key) can now be upgraded in place — the key actions menu has an "Add Subkey…" item that runs `gpg --quick-add-key` with the right algorithm (cv25519 / ed25519 / same-size RSA). This is **not** shown for smartcard or stripped keys, whose private key can't sign a new subkey.
- **Fixed: recipient pickers in the .siz and .szs create dialogs ignored the private keyring and offered sign-only keys.** Both now list encryption-capable keys from **both** keyrings (consistent with "Encrypt to GPG"), encrypt against the right keyring, and block mixing recipients from two keyrings in one operation. Sign-only keys no longer appear as recipients.
- **Fixed: recipient chips overflowed the dialog when several keys were selected.** Selected-recipient chips now wrap onto multiple lines instead of running off the right edge of the window (across all three encrypt dialogs).
- **Fixed: "Add Subkey" required a passphrase to confirm, and showed a placeholder mentioning a "UID".** Keys without a passphrase couldn't be upgraded at all; the confirm button no longer forces a non-empty passphrase, and the field text now correctly refers to the subkey.
- **New: edit a file inside a ZIP/7z and save it back.** Open an entry in an external app; when you return to SimpleZip, if the file was edited it asks whether to save the changes back into the archive — using the same safe write (copy → update → atomic replace), so the original is never damaged on failure.
- **New: edit a ZIP/7z in place from the right-click menu — Add Files…, Paste, Rename, and Delete entries.** When browsing inside an editable archive, the context menu gains these actions (whitelisted: they only appear for zip/7z, never for read-only formats like TAR/RAR or nested/temporary archives). Each goes through the Activity Center and the safe write path (copy → update copy → atomically replace), so the original archive is never damaged on failure. Deleting asks for confirmation.
- **New: drag files (or folders) into an open ZIP/7z to add them.** Dropping files onto an open zip/7z adds/replaces entries at the folder you're browsing, through the Activity Center, using a safe write (the archive is copied, updated on the copy, then atomically replaced — the original is never mutated on failure). Only the real, top-level archive accepts drops (not nested/temporary archives, not other formats).
- **"Get Info" (⌘I) is now in the File menu**, matching the right-click menu (it works on the selected files). Quick Look / Rename / Open With menu-bar parity is still pending — those are bound to the file list view.
- **Batch GPG encryption now reports per-item results instead of stopping at the first failure.** When encrypting several files one-by-one, each file is attempted independently; the Activity Center detail shows a ✓/⤼/✗ summary, lists the failed files with their reasons, and offers a "Retry failed items" button that re-runs only the ones that failed. (Per-item failure rows + the retry hook are generic, so other batch operations can adopt them later.)
- **New: a one-click Diagnostics report** in Settings → Health. "Copy Report" / "Export to File…" produce a redacted snapshot — app & macOS version, backend versions, GPG status, and a summary of the last 20 tasks — as the first thing to grab when reporting a problem. Passwords are stripped and no key identities are included.
- **New: a Format Capabilities table** in Settings → Archive shows, at a glance, what each container (ZIP / 7z / RAR / TAR / TAR.GZ / DMG / .gpg / .siz / .szs) supports — create, extract, encrypt, header encryption, split volumes, test, and comment — with RAR creation flagged as needing the rar tool.
- **Creating an archive whose output name already exists now honors the "When a file with the same name exists" preference** instead of silently failing with "destination already exists". Overwrite replaces it, Skip leaves it, and Ask (the default) shows Overwrite / Keep Both / Cancel.
- **Fixed: files encrypted to a private-keyring recipient could be encrypted but not decrypted** ("no secret key"). The secret key for a private-keyring recipient lives in SimpleZip's isolated GNUPGHOME, but decryption only ran against `~/.gnupg`. Decryption now tries `~/.gnupg` first and falls back to the private keyring, so a file encrypted to either keyring decrypts. (Symmetric-passphrase files succeed on the first try; truly missing secret keys still report a clear error.)
- **Fixed (archive safety): editing an encrypted ZIP/7z in place used to fail because the open password wasn't carried over.** Add / Delete / Rename / New entry and external write-back all passed an empty password, so editing a header-encrypted 7z (or AES zip) just errored. SimpleZip now reuses the password you unlocked the archive with — added/replaced entries are encrypted with the same password and header encryption is preserved (covered by a new round-trip test). Reloading the archive after an edit reuses that password silently, so you aren't re-prompted on every change.
- **Hardened (archive safety): in-archive entry paths now reject Windows-style escape paths.** Entry-path validation previously only blocked POSIX `/`, `.`, and `..`; a name like `..\evil.txt`, `C:\Users\x`, or `\\server\share\x` slipped through as an ordinary single segment that a Windows extractor would treat as a path separator / drive / UNC — a path-escape gap. Such paths (backslash separators, drive letters, UNC) are now rejected outright (never silently rewritten).
- **Fixed: dragging a folder containing empty subdirectories into an archive dropped the empty directories.** Folder drag-in only enumerated regular files, so empty (sub)directories were lost and the structure came out incomplete. Empty directories are now added explicitly, preserving the folder's shape (symlinks and special files are still skipped for safety).

## 0.3.0

- **Fixed: opening a nested archive (archive-inside-archive — a `.zip` in a `.zip`, a `.tar` in a `.tgz`, etc.) was broken once the encrypted scratch volume was in use, failing to open the inner archive.** The 0.2.7 encrypted scratch volume mounts via `hdiutil`, which reports its mount point as a `/private/var/…` realpath, but the "is this a disposable temp path?" check compared it (without resolving symlinks) against `FileManager.temporaryDirectory`'s `/var/…` form — so the check returned false, and opening the inner archive triggered the "leaving the archive" cleanup that **deleted the just-extracted inner archive before it could be read**. The check now resolves symlinks on both sides (and also recognizes the scratch volume's mount point), so nested archives open correctly again. (This also fixes opening a `.gpg`/`.siz` whose decrypted payload is an archive, which went through the same path.)
- **Fixed: opening a `.siz` / `.szs` / `.gpg` that lives *inside* an archive spawned a new window (`.siz`/`.szs`) or wrongly triggered the auto-extract float (`.gpg`).** These are SimpleZip's own file types, but when extracted from an archive they fell to `NSWorkspace.open`, which made macOS route the temp file back into SimpleZip as a fresh external open → a new window / the "auto-extract on open" path. They're now handled **in the current window** via their normal in-app flow: a nested `.siz` is unwrapped + signature-verified and its inner archive opens through the nested-archive path (address shows the `…/outer.7z/inner.siz` chain, "go up" returns to the real folder, no temp path leaked); a `.szs` opens its verification sheet; a `.gpg`/`.pgp`/`.asc`/`.key` is sniffed and decrypted/imported in place (only when GPG integration is enabled).
- **Fixed: Back (←) / Forward (→) / "go up" for an archive or `.siz` opened *inside* another archive didn't behave like Finder, and Forward could fail with "file not found".** Opening a nested archive (or nested `.siz`) now records the parent archive location (archive + sub-folder) in history: **"go up"** and **Back** return to that parent sub-folder (e.g. the `outer.zip/sub/` where the `.siz` lived) instead of jumping out to the physical containing folder; **Forward** returns into the nested archive without the previous failure (history navigation no longer purges temp archives that are still reachable via Back/Forward — only real navigation and closing the window do), and the address bar shows the nested chain instead of leaking the `/var/folders/…` temp path. A directly-opened (top-level) `.siz` / archive still goes up to its real containing folder as before; opening any new real archive/folder clears the nested return path.
- **Fixed: "Encrypt to .gpg" and "Create Symbolic Link" were only in the right-click menu — missing from the menu bar.** Both are now in the **File** menu too (the GPG one is gated on GPG integration being enabled + available, matching the signed-manifest item). (Broader right-click ↔ menu-bar parity for the remaining actions — rename / quick look / get info / open with — is still in progress.)
- **Fixed: opening a header-encrypted `.7z` (one where even the file list needs the password) didn't prompt for a password — it just failed.** The open flow only retried with a saved preset password; with no preset (or a wrong one) it fell straight through to an error instead of asking. It now shows the password dialog and retries — the same prompt-and-retry the extract flow already used — so a header-encrypted archive opens like any other password-protected archive. Cancelling the dialog quietly aborts (no error alert).
- **Fixed: "Generate revocation certificate" (Settings ▸ GPG) never worked.** `--gen-revoke` is an interactive-menu command; even when fed answers via `--command-fd`, gpg still tries to open `/dev/tty` for the prompts, and since SimpleZip spawns gpg without a controlling terminal it failed with `cannot open '/dev/tty'` before producing anything. Added `--no-tty` (a second latent bug also dropped an extra blank line that, with an empty description, answered gpg's final "Is this okay?" prompt as "no"). The save location is now chosen **inside the dialog** (a "Save to" row, defaulting to the Desktop) instead of a separate save panel popping up afterward, and the generated `.asc` is revealed in Finder so you can see exactly where it landed.
- **Fixed: a smartcard-backed key stopped showing as "on card" when the card was unplugged (and a normal local key could be misread).** The "on card / stripped / local" status comes from field 15 of `gpg --list-secret-keys --with-colons` (`+` = full local key, `#` = stripped, a serial = on a smartcard), but the parser read field 14 (always empty for `sec`/`ssb`), so it never detected the smartcard state on its own — it only worked while the card was inserted because a second path (`gpg --card-status`) filled the gap. With the card out, the key wrongly degraded to a plain local key. The parser now reads the correct field (and treats `+`/`#`/serial distinctly so a normal key is never mislabeled as on-card), covered by new parsing regression tests.
- **Fixed: dragging an entry out of an archive to Finder produced nothing.** The extraction actually succeeded, but the final move doubled the file name — `NSFilePromiseProvider` already hands back the full destination URL (drop folder + the name from `fileNameForType`), and the export code appended the name a second time, producing `…/name/name` whose parent folder doesn't exist, so the move failed and no file appeared. It now writes the extracted item directly to the promised URL. The file promise also now runs on a background operation queue (per AppKit's contract) so a large entry's extraction can't block the main thread while Finder waits.
- **Improved: dragging an entry out of an archive now shows up in the Activity Center.** The drag-out extraction used to run silently (no task, no progress, no way to cancel). It's now a managed task like every other extract — it appears in the Activity Center with a progress bar and can be cancelled mid-extraction (the dialog isn't forced open, so a quick drag stays unobtrusive).

Each split is a pure move (plus widening a few cross-file `private` helpers to module-internal), verified by the SwiftPM core tests and/or an Xcode Debug build._

- **Internal: split `GPGBackend` (1620 lines) into responsibility extensions.** The single enum is now an enum shell plus `GPGBackend+Discovery` / `+Keyring` / `+KeyManagement` / `+KeyLifecycle` / `+KeyCreation` / `+CryptoOperations` / `+Parsing`, with the nested data types in `GPGModels`. No public API change.
- **Internal: separated UI and models from `ArchiveExtractionCoordinator` (1266 → 814 lines).** The data models (`ConflictResolutionSession`, `PasteConflictChoice`, `TransferAction`, `TransferLogEntry`, `TransferStats`, `HashOverwriteResult`) moved to `ArchiveTransferModels`, and the conflict / transfer-summary SwiftUI views moved to `ArchiveConflictViews`. The conflict-decision + transfer + merge + hash-compare class is left cohesive on purpose (its private methods are densely interdependent and the area is data-safety-sensitive).
- **Internal: split `ExternalExtractWindow` (1092 → 408 lines).** The extraction runner moved to `ExternalExtractRunner`, the four float-window sessions (single / batch / prepare / create) to `ExternalExtractSessions`, and their SwiftUI content views to `ExternalExtractViews`; the window controller stays in `ExternalExtractWindow`.
- **Internal: extracted `GPGKeyRow` from `GPGPane` (1352 → 938 lines).** The 391-line keyring-row sub-view and the trust-level localization extension moved to `GPGKeyRow`. The Settings GPG pane View itself is left cohesive (state + body + actions); extracting an orchestration `GPGPaneModel` would change the pane's data flow and is deferred as a separate, hand-tested change rather than a pure move.
- **Internal: extracted the create / sign-`.siz` backend orchestration into a Core `ArchiveCreationService`.** `performCreateArchive`'s ~145-line task closure (plain create + GPG-signed `.siz` assembly) moved verbatim into `SimpleZip/Core/ArchiveCreationService.swift` (now SwiftPM-testable); the model just calls it inside `startManagedArchiveTask`. Pure move, no behavior change.
- **Internal: extracted shared GPG recipient-picker controls.** The add-recipient `Menu`, recipient chip, and chip row were duplicated verbatim across `GPGEncryptOptionsView` / `ArchiveCreationOptionsView` / `CreateSZSSheet`; moved into `Features/GPG/GPGRecipientControls.swift` (`GPGRecipientChip` / `GPGAddRecipientMenu` / `GPGRecipientChipRow`). Each dialog keeps its own row layout and key-lookup set, so behavior is unchanged — only the duplicated inner widgets are shared.
- **Internal: extracted the shared single-select signing/decryption-key `Menu`.** The "auto + secret-key list + three-state button label" picker was duplicated verbatim across four dialogs — `ArchiveCreationOptionsView` & `CreateSZSSheet` (signing key) and `ExtractArchiveOptionsView` & `SIZSignatureSheet` (decryption key); moved into `Features/GPG/GPGSecretKeyMenu.swift`. The auto / missing-fingerprint L10n keys and the selection binding are passed in, and each dialog keeps its own row layout (label font / alignment / padding), so behavior is unchanged — only the duplicated inner menu is shared.
- **Internal: shared the sidebar collapse/expand toolbar button.** The Settings window and the Activity Center each hand-wrote an identical sidebar-toggle button (same image size / 20×20 frame / borderless / `.controlSize(.small)`), differing only in the `.help` tooltip; moved into a shared `SidebarToggleButton` view with the help text passed in. No behavior change.
- **Internal: the Activity Center settings rows now reuse `SettingsControlRow`.** Its private `activitySettingsRow` helper was a byte-for-byte copy of `SettingsControlRow.body`; the two call sites now use `SettingsControlRow` directly and the duplicate helper is gone. No behavior change.
- **Internal: consolidated the `.siz`-open hand-off into a single `SIZOpenRequest`.** Opening a `.siz` in-app used to set three separate model fields (the pending URL, a display-anchor override for `.gpg`-wrapped `.siz`, and a nested-entry chain for a `.siz` opened from inside another archive), each set at its own call site and read/cleared independently in `handleSIZOpen` — so a leftover anchor or entry chain could bleed into the next open. They're now one atomic `SIZOpenRequest { url, displayOverride, nestedEntryName }` that `onChange` consumes whole. No behavior change.
- **Internal: moved unique-file-name computation into a testable Core `UniqueFileName`.** "Make a Copy" and "Create Symbolic Link" each hand-rolled an identical incrementing-name routine (base + suffix → base + "suffix 2" → …), differing only in the suffix word and the exists-check (symlinks need `lstat` to spot a dead link that `fileExists` follows through). They — plus the new-folder/new-file numbering — now call `UniqueFileName.suffixed(…)` / `.numbered(…)` in `SimpleZip/Core`, with the exists strategy injected as a closure and the localized suffix passed in. Pure logic, SwiftPM-tested, no behavior change. (First slice of slimming `ArchiveBrowserModel`'s file-operation ownership.)
- **Internal: moved the undo/redo "file unchanged?" safety check into a testable Core `UndoFileSnapshot`.** This is the data-safety primitive behind the repo rule "never silently overwrite user data": before each undo/redo step it confirms the source still exists and hasn't been altered (type + size + mtime + device + inode), and skips the step otherwise. It was a private, untested struct inside the undo extension; moved verbatim to `SimpleZip/Core` with regression tests (unchanged file matches; content change, delete-and-recreate, or deletion all correctly fail to match). The recursive `performUndoable*` orchestration stays in the model (it's tightly coupled to `NSUndoManager`). No behavior change.

## 0.2.7

- **Fixed: opening a `.siz` that was wrapped in a `.gpg` leaked the raw `/var/folders/…` scratch path into the address bar.** Decrypting a `<name>.siz.gpg` produced the inner `.siz` in the encrypted scratch volume and then showed it as a loose file; opening it ran the signature flow anchored to that scratch path. SimpleZip now decrypts and routes the inner `.siz` straight through its unwrap + signature-verification flow (so tampering is still caught), with the address bar anchored to the original `.gpg` — the temp path is never shown, and "go up" returns to the `.gpg`'s real folder.
- **Right-click → "Create Symbolic Link".** Makes a symlink next to each selected file/folder (named `<name> symlink`, never overwriting), pointing at the original by a **relative** path (just the filename) so the link keeps working if you move the whole folder. Supports multi-selection, is undoable (⌘Z removes the created links), and is recorded in the Activity Center. (If "show symbolic links" is turned off in View settings, the new link won't appear in the list until you re-enable it.)

- **Double-click a GPG-encrypted file (`.gpg` / `.pgp`) to open it, like a password-protected archive.** SimpleZip decrypts the file (gpg-agent / pinentry prompts for the passphrase — SimpleZip never handles your GPG private-key passphrase; a status indicator shows "Decrypting…" while you authorize) and then opens the result **inside SimpleZip, never dumped to Finder**: if it's an archive it's browsed in place, otherwise the decrypted file is shown in SimpleZip's own browser — in both cases the address bar shows the original `.gpg` name, not the temp path. Crucially, a `.gpg`/`.pgp`/`.asc` file is **not assumed to be encrypted data by its extension** — SimpleZip sniffs the content first by reading the OpenPGP packet header (armor line / first packet tag — it never runs a decrypt, never prompts, never returns the wrong "not encrypted" message when you cancel): public/private **key** exports are routed to an "import into keyring" dialog instead of being decrypted, and detached signatures are left alone. Opening from Finder reuses the current window instead of spawning a new tab. Requires GPG integration to be enabled in Settings ▸ GPG.
- **Fixed: opening a nested archive (an archive inside an archive — a `.tar` inside a `.tgz`, a zip inside a zip, etc.) leaked the raw `/var/folders/…` temp path and broke "go up".** Nested archive entries used to be handed to the OS, which re-opened the extracted copy from a temp folder with no context — so the address bar and "go up" exposed `/var/folders/…`. Nested archives now open **in place inside SimpleZip**, and the address bar stacks the whole nesting chain as virtual folders so you can see where you are at any depth (e.g. `…/Desktop/xx.zip/xa/a.zip/b.zip/c.zip`); "go up" from a nested archive returns to the outermost archive's real folder, never the temp path.
- **Decrypted / extracted temp files now live in a per-session encrypted scratch volume, and are cleaned the moment you close an archive.** Previously the plaintext SimpleZip extracts/decrypts to (when you open a `.gpg`/`.siz`, browse an archive, or open a file inside one) sat unencrypted under `/var/folders/…` until the next launch — which defeats the point of encryption. Now, on first need, SimpleZip mounts an **AES-256 encrypted disk image keyed by a random password that exists only in memory for this session**; all temp content goes inside it, it's detached and deleted on quit, and any image left by a crash is swept on next launch (the file on disk is ciphertext — unopenable without the in-memory key). Decrypting a `.gpg`/`.siz` is **fail-closed**: it refuses to write plaintext anywhere but the encrypted volume (if the volume can't mount, the open errors instead of leaking plaintext); if the volume is unmounted mid-session it is detected and transparently re-mounted before any decrypt. And leaving an archive (going to a folder / opening another) now **purges that archive's temp immediately**, not just on quit.
- **Fixed: a wrong decryption password in the `.siz` signature dialog gave no feedback at all.** The error was posted to an alert that sat *behind* the still-open sheet, so nothing appeared. The dialog now shows the decryption failure inline (in red) and stays open so you can fix the password / key and retry, with a spinner while decrypting.
- **Right-click any file or folder → "Encrypt to .gpg…".** A compact sheet lets you pick recipient public keys, a passphrase, or both (anyone holding a recipient's private key *or* the passphrase can decrypt — SimpleZip never handles your GPG private-key passphrase; the symmetric passphrase field auto-fills from your preset password if you have one set). A single file becomes `name.gpg`. When the selection has multiple items or a folder, you choose how to encrypt: **each file separately** (the default — folders are recursed and every file inside is encrypted to its own `<name>.gpg` right next to it, e.g. `folder/sub/b.txt` → `folder/sub/b.txt.gpg`) or **packed into one archive** (everything, including folder structure, into a single `.tar.gpg`). Any `.tar` staging happens inside the encrypted scratch volume — plaintext is never written in the clear to ordinary disk. Output is selected in SimpleZip's own folder list (it does not pull Finder forward), and the whole thing runs as a cancellable Activity Center task that lists each produced `.gpg`. Only shown when GPG integration is enabled in Settings ▸ GPG.
- **Creating a signed manifest (`.szs`) can now encrypt the listed files to `.gpg` at the same time.** The "Create Signed Manifest" sheet gains an "Encrypt the listed files to .gpg" option (pick recipient public keys, a passphrase, or both). When on, each selected file is encrypted to a `<name>.gpg` next to the original (originals are kept) and the manifest then covers those `.gpg` files (their hashes) — so you distribute the signed manifest plus the encrypted `.gpg` files, and recipients verify the signature before decrypting each file with their key or passphrase. The manifest itself stays a plaintext signed file (it only holds hashes — there's no point encrypting it). Encrypting to a public key needs no passphrase or touch; only the signing step uses your key.
- **"Auto-extract on Finder open" now covers GPG-encrypted files.** With that preference on, opening a `.gpg`/`.pgp`/`.asc` whose content is encrypted data now decrypts it in a detached float window (decryption uses your gpg-agent / smartcard exactly as before — encrypting to a public key needs no passphrase or touch, only decrypting does) and drops the result next to the original, completely decoupled from the main window — the same way archives and `.siz` auto-extract. If the decrypted payload is itself an archive (e.g. `backup.tar.gpg`) it's unpacked into that folder; a plain file (e.g. `report.pdf.gpg`) is placed there directly. Key material and signatures still route to the main window (import dialog / message), and with the preference off nothing changes.
- **Open a `.asc` / `.key` key file to import it into a keyring.** `.asc` and `.key` are now registered (Alternate-rank, so they won't steal your default text-editor / Keynote association) file types: opening one — by double-click in SimpleZip's browser or from Finder — sniffs the content and, if it's a public/private key export, brings up the "import into the user keyring or SimpleZip's private keyring" dialog. The same content-first routing applies in the in-app browser to `.gpg`/`.pgp`/`.asc`/`.key` (directory packages such as Keynote documents are excluded), and only when GPG integration is enabled in Settings ▸ GPG (otherwise the file opens with the system default app).

- **`.szs` Signed Manifest format v1, end-to-end implementation** (design + Core + GPG + UI + UTI)
  - **Format**: a `.szs` is a GPG clearsigned JSON manifest. **One signed manifest + N external files staying in place** — complementary to `.siz` (single-file container). Use cases: release drops (app + LICENSE + README + checksums.txt), mirror trees, per-file integrity verification. `cat foo.szs` shows the JSON; `gpg --verify foo.szs` works as a one-shot CLI verification; single-file, no sidecar `.sig`.
  - **Schema**: `{schema: "SimpleZip.szs", version: 1, createdAt, files: [{relativePath, size, sha256, mediaType?}], …}`. The `files` array is lexicographically sorted by `relativePath` (precondition for deterministic signatures). No directory entries, no symlinks, no mode bits, no mtime; `relativePath` goes through `validatedRelativePath` which rejects `..`, Windows drives, UNC, backslashes, and other unsafe components. **Full spec at `docs/SZS-FORMAT.md`**.
  - **Core implementation** (`SimpleZip/Core/SZSArchive.swift`): `Manifest` / `FileEntry` / `EncryptionInfo` types + `create(payloadRoot:files:signingKey:title:description:outputURL:)` + `verify(manifestURL:payloadRoot:)` + `peek(manifestURL:)` + deterministic `encodeManifest`. SHA256 reuses `SIZArchive.computeInnerArchiveSHA256` (1 MiB streaming chunks); large files don't blow up memory.
  - **GPG backend** (`GPGBackend`): new `clearsign(plaintextURL:signingKeyFingerprint:outputURL:)` + `verifyClearsign(signedURL:)` → returns `(GPGVerifyResult, plaintext: Data)`. Reuses `.siz`'s `--status-fd 1` parsing and two-pass merge (user keyring + SimpleZip-private ring).
  - **UI**:
    - `SZSVerificationSheet` (verification report) — signature status at the top (reuses `SIZSignatureStatus`'s icon / color / title mapping) + manifest metadata (title / description / created at / file count) + selectable payload root + per-file table with ✓/✗/⚠ badges per row; mismatched rows expand to show expected vs. actual SHA256;
    - `CreateSZSSheet` (creation dialog) — pick payload root + multi-select files + optional title / description + signing-key picker + output location; file list shows relative paths with × buttons to remove; success auto-closes after 1.5s.
  - **Menu + file association**: a "Create Signed Manifest… (⇧⌘N)" entry is added to the File menu (only shown when `gpgEnabled` and the GPG backend is available); `Info.plist` registers the `com.simplezip.szs-manifest` UTI so Finder double-clicks route into SimpleZip.
  - **`ContentView.handleSZSOpen`**: peek manifest → presents `SZSVerificationSheet`, default payload root = the directory containing the `.szs`, with a button to switch to a different directory and re-verify.
  - **Encryption deliberately deferred** — `.szs` v1 is sign-only. Encryption use cases are served by `.siz` v3 (single-archive, multi-recipient); mixing encryption into a per-file manifest introduces too many edge cases.

- **`.siz` tamper-resistance hardening (schema bumped to v2, breaking)**
  - The signing target changed from the inner archive to `metadata.json`: under v1 an attacker could rewrite the signer name / timestamp / `innerArchiveName` in `metadata.json` while the inner-archive signature stayed valid, so the UI would display forged information. Mutating any byte of `metadata.json` now makes gpg verification fail outright.
  - Inner archive content is locked by a new `innerArchiveSHA256` field in metadata (streamed SHA256, not loaded whole into memory). `SIZArchive.verify` performs gpg verification of the metadata signature **and** recomputes the inner archive SHA, downgrading to `.badSignature` on mismatch — so swapping the inner archive can't hide either.
